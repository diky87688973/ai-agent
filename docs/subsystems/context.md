# Context management

The context pipeline answers two questions: **what the request body sent to the model consists of**, and **how history is compacted when it grows too long**.

The implementation is in `agent/mechanisms/context/` (turns, layout, sources, and assembly) and `agent/mechanisms/compaction/compactor.py` (compaction and summaries).

## Three-part assembly

The request body has exactly three parts:

```
messages = head + dialogue + tail

head = system prompt + plugin segments + memory summaries
dialogue = turns folded from session facts
tail = current-turn new input / tool results + execution mode
```

**The only assembly entry point is `ContextPipeline.assembles(tail)`.** A normal request:

```python
messages = pipeline.assembles([new_input, mode_note])
```

For compaction, the tail is removed first and appended again afterwards:

```python
zip_messages = compress(pipeline.assembles([]))   # no tail
messages     = pipeline.assembles([new_input, mode_note])
```

Assembly is **synchronous**: nothing proceeds until compaction finishes. `rebuild_from_messages()` is a compatibility forwarder to `set_dialogue()`, not a second assembly path: reconstructing the head from `messages` drops the system prompt and plugin segments (they are not in the fact log).

## Five chunks

The pipeline holds content per chunk. `CHUNK_ORDER` fixes the flattening order, and empty chunks are skipped.

| Constant | Chunk | Content |
|---|---|---|
| `CHUNK_SYSTEM` | system prompt | base prompt + plugin prompt sections + tool summary |
| `CHUNK_PLUGIN` | plugin segments | content injected by plugins as segments |
| `CHUNK_MEM` | memory summaries | summaries produced by each compaction, one `system` message each |
| `CHUNK_FULL` | recent memory | dialogue turns, kept verbatim apart from the reasoning replay budget |
| `CHUNK_MODE` | mode | kept for structure; the execution mode is assembled into the request tail and does not populate this chunk |

## System prompt sections

The system prompt ends up as one `system` message, but it is composed of ordered sections:

```text
identity → reply language → action discipline
→ plugin sections (PromptSections, plugin-manifest order; e.g. `## 资源目录`)
→ environment information → coding guidelines → terminology → tool-use discipline → tool summary
```

- The base sections are produced by `prompts.py:build_system_prompt()`; `resolve_system_prompt()` cuts the mode section, and the execution mode travels in the request tail.
- Plugins register sections with `ctx.add_prompt_section(section, fn)`; `section` is the full heading. Bodies registered under the same heading are merged, and the heading appears once. Sections belong to the system prompt and do not occupy a context segment of their own.
- `## 资源目录` is registered by the Skills and Rules plugins; `## 动手指令` is a base section placed immediately after the reply-language section.
- `## 环境信息` is generated by the session runner for the current session: operating system and this session's ID.
- `## 可用工具` lists tool names with a one-line summary; full schemas travel only in the request's `tools` field.

## Assembly order

**Order follows likelihood of change: the less a part changes, the earlier it goes.**

```text
system prompt → memory summaries → recent memory      fixed relative order; does not vary with plugins
plugin segments as a group                            between the system prompt and the memory summaries
plugin segments among themselves                      plugin-manifest order (plugins.ini); earlier plugins first
mode                                                  last
```

The manifest order is the assembly order: two sections' order in the manifest is their order in the request. A plugin placed earlier should be the one less likely to change; plugins whose content changes with UI actions come after read-only ones. Application-level sources (not owned by any plugin, registered directly through `ContextSources.add`) have no manifest rank and come after all plugin segments.

Implemented in `ContextSources.collect_segments()`: a stable sort by `SourceMeta.plugin_rank`. The host writes `plugin_rank` when loading plugins, using the manifest index (`PluginContext.set_rank`).

## Kernel and plugin collaboration

**The kernel knows no specific plugin.** It only knows that "a source registered a segment":

```python
@dataclass(frozen=True)
class SourceMeta:
    key: str = ""          # segment key = plugin name (the frontend uses it to find the plugin's render hook)
    label: str = ""        # segment label
    plugin: str = ""       # owning plugin name
    prefix: str = ""       # injection prefix telling the model what this segment is
    count: Callable[[str], int] | None = None   # subject-count callable fn(cid) -> int
    plugin_rank: int | None = None              # plugin position in the manifest = assembly position
```

A plugin has one entry point:

```python
ctx.add_context_source(fn, {"label": "segment name", "prefix": "<prefix>\n",
                            "count": subject_count_callable})
```

- `fn(conversation_id) -> list[str]`; each string becomes its own `system` message.
- One plugin can register **multiple sources**; they share the segment key and each occupies a row in the layout.
- `prefix` is supplied by the source and applied by the host during collection; a wrong prefix makes the model treat the segment as dialogue.
- An error in one source is isolated (written to stderr) and does not affect other sources or the request.

Collection returns one structure:

```python
PluginSegments(items=[(segment_key, label, body)], counts=[subject counts by position])
```

`counts` correspond **by position**, not by key: two segments of the same plugin share the segment key, and storing them by key would make them overwrite each other.

### What the kernel does with plugin segments

| Stage | Kernel action |
|---|---|
| Collection | sort by `plugin_rank`, apply prefixes, isolate errors, read subject counts |
| Assembly | each segment becomes a `system` message in `CHUNK_PLUGIN` order, all within the head |
| Breakdown | one row per segment; `key` is `plugin:<plugin name>`; label and count come from the plugin |
| Flattening | `flatten_to_messages()` passes the final list through `sanitize_fn` |

The kernel does not interpret what a label or a count means: whether `count` is "how many files" or "how many skills" is decided by the plugin.

### Observability

After each request assembly the kernel emits one `context_segments` event (from `ModelModule`) whose payload is the result of `layout_payload()`. The classic UI adapter derives `context_layout` from it: dialogue, system-prompt, and mode rows come from that snapshot; plugin segments are overlaid from the current injection sources; percentages and remaining capacity are recomputed against the current budget.

A session without a snapshot falls back to `layout_from_messages()`: it performs one real assembly (plugin content is not in the fact log and can only come from injection sources) and splits the head by the source descriptions.

## Segment statistics

`ContextPipeline.segment_tokens()` estimates tokens per segment using the same accounting as the request actually sent (the same `default_message_tokens`).

| key | Source | `count` basis |
|---|---|---|
| `system` | system prompt | message count |
| `plugin:<plugin name>` | one row per plugin-registered segment | plugin-reported; message count by default |
| `summary` | compaction summaries | message count |
| `full_recent` | recent dialogue | **user rounds** (a round contains the question, the answer, and tool round-trips) |
| `mode` | **request tail**, not in the pipeline | computed separately through `layout_payload(tail_messages=…)` |

`layout_payload()` adds `remaining` (remaining capacity) and `pct`; server-side `pct` uses `budget_tokens` as the denominator, and that value is the larger of the compaction threshold and the used total. The UI recomputes display percentages and remaining capacity from `model_max_context_tokens`, falling back to the budget when that is 0. The budget percentage is a display concern; compaction is triggered by the threshold.

Reported counts align with sources **by position**: the count list returned by `collect_segments()` has the same length as the segment list, and a source without a reported count uses its own message count. Misalignment is silent — labels and tokens stay correct and only the number is wrong — so neither side may fill in a neighboring segment's count.

### Fields and limits

`context_layout` top-level fields:

| Field | Meaning |
|---|---|
| `segments` | segment list, always ending with `remaining` |
| `total_tokens` | total occupied by all segments and the tail (excluding remaining capacity) |
| `budget_tokens` | actual denominator for segment `pct` (the larger of the compaction budget and the used total) |
| `model_max_context_tokens` | current model window; 0 when unknown, in which case the UI falls back to the budget |

`context_layout.segments[]` carries **data only**:

| Field | Meaning |
|---|---|
| `key` | segment identifier; plugin segments use `plugin:<plugin name>`, the remaining segment uses `remaining` |
| `label` | segment label (plugin-reported) |
| `tokens` | tokens occupied by this segment |
| `count` | subject count (plugin-reported; message count by default) |
| `pct` | share of the budget |

`segments` always ends with `{"key": "remaining", "label": "剩余容量", "tokens": ..., "pct": ...}`; this entry has no `count`.

**Colors, icons, and layout belong to the UI**: the layout payload carries no color values. Plugins register appearance through `ctx.add_ctx_segment_style(label=..., color=...)`; at startup the shell fetches `/api/ctx-segment-styles` and calls `ctxSegments.register`. Registration happens before the first render, so the segment bar and the tooltip use the same source and the same color. When a plugin has not registered, the shell picks a stable color from its own palette by segment key. Panel scripts may preload at startup; panel styles are injected on demand.

## User rounds are atomic

One `user` message up to the next `user` message is **one user turn**. Compaction only processes whole turns:

- When delimiting the range to compact, the boundary is **rounded down to a round boundary** (`turn_boundary_floor`): rather than compacting part of a round, that round is left alone.
- The cut is also bound by a hard constraint: it must not split a **dangling tool chain** (`tool_chain_balanced`). An `assistant.tool_calls` message and its `tool` results must be kept together, or the model API rejects the request with 400.

## Tool round-trips are not stripped

**Normal requests only append tool round-trips**: tool round-trips already sent are kept byte-for-byte in later requests. Rewriting any middle message invalidates the provider's prefix cache from that message on — and the agent appends tool round-trips every turn, so rewriting middle content each turn would drive the cache hit rate to zero.

Tool round-trips are therefore **not** subject to "keep the last N rounds and strip earlier ones":

- Tool round-trips outside the compaction range are kept as-is; none are dropped.
- Those inside the compaction range are part of the summary request prefix: the summarizer sees that segment **with the original tool results**, and the summary takes over for those results.
- The cut is constrained by `tool_chain_balanced` and never splits a dangling tool chain (an `assistant.tool_calls` message and its `tool` results must stay together, or the model API rejects the request with 400).

`set_dialogue` drops the prefix already covered by summaries (`covered_end`) and applies the reasoning replay budget; everything else loads unchanged. With each new turn, the context is the previous context **plus the new messages**.

## Compaction trigger

### How the threshold is derived

With a model window:

```text
threshold = floor(context_window × compression_percent / 100)
```

`compression_percent` belongs to the model entry: default 70, range 10–90. When the model declares no window, `[context] summary_token_fallback` is used (default 64000).

It is a **soft cap on request size**, not a target for how far to compact:

```
estimated size = estimated tokens of the request sent to the model
               = system prompt + plugin segments + memory summaries + uncovered dialogue + pending messages
                 + fixed overhead of tool schemas and the mode note

estimated size <= threshold  →  pass through, send as-is
estimated size >  threshold  →  compact existing history first, then send with the compacted context
```

The size is an **estimate** (`approx_tokens_text` / `default_message_tokens`), not an exact count. It is also the percentage base for the layout view: `context_layout.budget_tokens` takes the larger of this estimate and the used total, and each segment's `pct` is computed against that field. The threshold follows the session's current model and is recomputed on the next turn after a model switch.

Exceeding the threshold **is not an error**: compact and keep going. It is the only number that decides whether compaction should run.

### Full compaction flow

`ContextCompactor.ensure_before_append()` runs before appending:

```
1. take the uncovered view   view = messages[covered_end:]      ← the already compacted prefix is not revisited
2. build the base            base = full assembly - tail (current-turn new input + execution mode)
3. estimate and compare      total_token_estimate(base) + pending + fixed overhead > threshold ?
                             no  → return None (pass through)
4. choose the excerpt        excerpt_by_target_tokens(view, keep_turns=full_user_rounds)
                             ├ mask the last full_user_rounds user rounds (the near field stays)
                             ├ take the range before the mask; if there is nothing there, compact the mask too
                             └ cut back to a round boundary (turn_boundary_floor) and a tool-chain boundary
                               (tool_chain_balanced); if it cannot, abandon this compaction
5. call the summarizer      use base as the prefix and append the compaction instruction
                            (the prefix is byte-identical to a normal request)
                            the compacted segment (including original tool results) is already in the prefix
6. record                   covered_end += range length; append the summary to summaries
7. install it immediately   set_summary_messages(): the same request is assembled next and must
                            read the new summary (a delay would send the request with stale context)
```

### Masking

The last `full_user_rounds` user rounds are the **mask**: that is the model's near field, where the current work lives.

- Normal path: the mask stays, and the segment before it is compacted.
- When there is no room before the mask (only one round in total, or the mask covers everything), **the mask is compacted too** — in the extreme case the compacted context has **0 user rounds**, the summary takes over all history, and only the head remains.
- The mask is a **preference**, not a reason to refuse compaction: if nothing can be compacted, the request simply exceeds the limit and fails.

The system prompt and plugin segments are all `system` messages placed before the dialogue, so the region "after the last leading `system`" **naturally covers only dialogue** and contains no system settings.

### How the excerpt is chosen

`excerpt_by_target_tokens(messages, keep_turns)` returns the range `[0, cut)` to compact:

- `cut` is the **start of the mask**: the range does not include the masked turns.
- When there is nothing before the mask, `cut` falls at the end — **0 user rounds** is a valid result.
- The cut has been validated against turn boundaries and tool-chain boundaries; if it cannot retreat, it returns `None` (nothing is compacted this time).

### Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `threshold` | computed per model | soft cap on request size; compaction starts above it, and it is the base for layout percentages |
| `summary_token_fallback` | 64000 | fallback threshold when the model declares no window; configuration file only |
| `full_user_rounds` | 5 | number of trailing user rounds masked (compacted along with the rest when no room remains) |
| `summary_output_max_chars` | 5000 | summary length limit (characters) |
| summary prefix | always reused | summary requests carry the same prefix as normal requests, so the call hits the existing cache |

### Transient runtime tail

Before each model pass, the host temporarily appends one `system` message at the end of the request:

```text
## 当前模式：...

## Todo-List：**必须实时追踪并更新任务进度**
当前进度：X 已完成，Y 进行中，Z 待处理

[plugin prompt tail]
```

The Todo-List lines are present only when a todo list exists and a mode note is present.

This tail:

- is re-evaluated on every pass; after a tool checkbox update, the next pass reads the latest `LiveState`;
- is not persisted, not emitted as an event, and not compacted;
- is stripped of any leftover transient tail before assembly, to avoid duplicate appending;
- uses the same counting rules for todo progress as the UI.

**Compaction is synchronous**: the request is not sent until compaction finishes; what goes out must be the compacted context.
**Compaction is an enhancement and never blocks a turn**: a missing compactor, a failed call, or empty summary text all pass through (errors are logged to stderr, never swallowed silently).

`ContextCompactor.restore_from_events()` replays `context_compacted` events from the session record to rebuild state (idempotent; `covered_end` never decreases).

## Summary requests reuse the prefix

A summary is also a model call: **the structure matches a normal request, and only the ending differs**:

```
normal request   system prompt + plugin segments + memory summaries + dialogue + new input / tool results + execution mode
summary request  system prompt + plugin segments + memory summaries + dialogue + compaction instruction
```

The prefix is intended to be the previous request's prefix with the tail removed, so this part can hit the provider's KV cache. In current compaction, bases assembled before late summary installation and reasoning cleared in the summary copy may differ; cache reuse is therefore best-effort rather than guaranteed byte equality.

**It must be the whole prefix**: cutting a segment out of the middle means it is no longer the previous request's prefix, and the cache is invalidated from that point on. Two things must match; one missing invalidates the whole prefix:

| Item | Source |
|---|---|
| message prefix | the **same** assembly result as a normal request, with the compaction instruction at the end |
| `tools` | the same schema as this request (`ModelModule` passes it to `ensure_before_append`) |

The system prompt is carried by that prefix (its leading `system` messages); no separate system field is sent. The execution-mode note is **not** part of the prefix: `ensure_before_append` strips the trailing mode note (`mode_note` / `MODE_MARKER`) before building the summary request, and the compaction instruction takes its place.

The instruction is a **final `system` message** stating that the head segments (system prompt, plugin segments, memory summaries) are the agent's persistent setup, not dialogue content.

When no prefix is available, the fallback is another path: one user message containing the material as role-tagged text, followed by the same instruction as a trailing `system` message.

## Execution mode is a transient suffix on the request tail

Execution mode (Auto / Plan / Execute) is **not in the system prompt**, and does not enter the session record or events: `resolve_mode_note()` in `shell/prompts.py` produces it separately, and assembly appends it as the last message. When a todo list exists, a fixed `## Todo-List：**必须实时追踪并更新任务进度**` maintenance hint follows the mode. The plugin's own request tail (such as AI Speak) is appended in the same tail message.

If the mode were part of the system prompt, every mode switch would modify the first block of the context and invalidate the entire prefix cache from that point. At the tail, a switch changes only the last message.

```text
system prompt + plugin segments + memory summaries + dialogue + new input / tool results + execution mode
                                                              + Todo-List
                                                              + plugin request tail
                                                                  ↑ appended transiently
```

`build_system_prompt()` produces the mode section (for standalone use); `split_mode_section()` removes it from the system prompt, deleting only the mode section itself and keeping the plugin sections and tool summary that follow.

When the caller supplies an explicit system prompt (the mesh `system` field), neither the mode note nor the Todo-List hint is appended.

`ensure_before_append()` removes the trailing mode note before compaction (`_strip_mode_tail`), so it is not summarized as dialogue content.

## Multi-segment plugins

A plugin can register **multiple** injection sources; they share the segment key (the plugin name) and each occupies a row in the layout. `plugins/skills` is such a case: one catalog segment and one resident-body segment, each with its own label and heading.

Multiple injections form **one source group**: assembly position comes from the plugin's position in the manifest, and within the group registration order is used. Segment statistics report rows in the same order.

The Skills plugin's own layering is covered in [skills.md](skills.md).

## Image limits in the request

Images are inlined into the request body, so their number must be managed explicitly (both limits live in `[context]`):

| Parameter | Default | Meaning |
|---|---|---|
| `image_turns` | 1 | Embed images only from the **most recent N user rounds**; older user images become text placeholders. Tool-result images are not limited by this setting. Negative = unlimited |
| `image_max` | 8 | Total images in the request (user and tool images combined); **the newest images are preserved first**, and excess images are dropped starting from the oldest. Negative = unlimited |

The turn limit counts turns, not images: three images in one turn count as one turn. "This image" refers to the turn just sent; older images carry little value but still occupy real space in the request.

Stripped images disappear only from **the copy sent to the model**: the base64 in the fact stream is untouched, so history replay and re-asking still have the original image. Detection and placeholder text live in `image_embed.strip_old_images()`.

## Summary generation

`make_provider_summarizer(provider)` returns a summarize function. With a reusable prefix it sends that prefix plus a fixed instruction; without one it serializes the material into a user message. Either path is a **single-turn** model request and returns the text. When the prefix is reused, the same tool schemas ride along as part of the cached prefix; the instruction forbids tool calls.

The summary prompt asks for sections (background / key conclusions / constraints and agreements / unfinished and unconfirmed / risks and caveats) and states explicitly: do not invent content that is not in the record.

`max_chars` **is written into the prompt as a length constraint only; the code does not truncate**. The actual length depends on how well the model follows it.

Degenerate detection `_is_degenerate_summary_body()`: an empty body, or a body shorter than 10 characters containing the `摘要为空` placeholder, counts as failure.

## Estimation

The estimator `approx_tokens_text()` counts by character class: **1 token per CJK character, 1 token per 4 other characters**. `default_message_tokens()` also counts the `arguments` of `tool_calls`; estimating everything as `len // 4` would underestimate Chinese text roughly fourfold, invalidating the threshold and pushing compaction far past the intended point.

Compaction checks add the fixed overhead of tool declarations and the mode note (they are not in `messages` but are part of the request body).

`reasoning_content` is counted after clipping by `reasoning_replay_tokens`: what is sent back is what is billed, and estimation uses the same copy.

The segment tooltip shows an **estimate** (the sum over the assembled `messages`), not the `prompt_tokens` in the usage bar: the latter is the true value returned by the API. The two differ by tool declarations and tokenization.

Token counts are **estimates**, not exact counts:

- `approx_tokens_text()`: estimates text by character class;
- `default_message_tokens()`: estimates by message structure;
- images count as a fixed `IMAGE_TOKENS_PER_IMAGE` (fixed at 384, not read from configuration).
