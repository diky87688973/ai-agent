# 动手规则

## P0 红线：没有明确修改指令，禁止任何写操作

本条是写入门槛，优先于其他规则中的执行选择。已获得修改授权后，再由架构规则决定怎么改。授权只按下列判据认定，不按语句强弱或主观把握认定。

### 授权成立（三条同时成立才算）

1. 用户消息中存在独立成句的动作指令，动词落在 改 / 修 / 删 / 加 / 提交 / 推送 / 重启 / 执行 之一。
2. 该动词指向本轮的写盘对象（文件、命令、分支），不从上一轮答复里推断。
3. 涉及两个及以上文件时，改动清单（文件:行、原样、改成、影响）已先提交，且本次指令晚于该清单。

### 一律不算授权

4. 动作词出现在答复、说明、参数讨论、条件句、疑问句中。
5. 用户在回答助手提出的澄清问题。
6. 用户确认方案细节、取值、范围、取舍、格式。
7. 用户复述、引用或评价助手输出。
8. 用户仅表示同意、认可、知道了、继续。
9. 助手从上下文推出「用户应该会同意」。
10. 是否构成授权无法判定时，一律按不授权处理，不动手。

### 时序门

11. 无授权时只允许只读动作：读文件、检索、查询、跑测试与门禁，不得改变源码、配置、规则与提交状态。
12. 改动清单本身不构成授权；提交清单后必须停下，等下一步用户消息。
13. 该下一条消息若同时含提问、条件或解释，即使带动作词也不得写盘。
14. 多轮讨论中，授权不能跨轮累积：上一轮的许可不覆盖本轮的写盘。

### 违反即最高级事故

15. 未经授权的写操作立即停手，不得新增任何写操作。
16. 当场列出全部改动（文件:行、原样、改成、影响），由用户决定回滚或保留。
17. 不得以「已经改完」「影响很小」「为了效率」为由继续。
18. 不得自行回滚：回滚也是写操作，同样需要指令。

工程复核的触发、只读边界与全量 CI 例外，按 [PROJECT_CHECK.md](PROJECT_CHECK.md) 执行。
