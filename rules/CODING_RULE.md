# 编码规则

## P0-1 动态列表事件委托

**由 JavaScript 动态创建或重渲染的列表项、卡片、行、按钮，禁止逐个绑定事件监听器**

- 事件必须委托到稳定的顶层容器，例如 `document` 或列表根容器
- 通过 `event.target.closest(selector)` 定位具体元素，再读取 `data-*` 等属性分派行为
- 禁止对每个动态元素执行 `addEventListener(...)`、`onclick = ...` 或其他逐项绑定
- 顶层监听器只能注册一次；重复初始化必须幂等
- 键盘事件同样遵守顶层委托
- 静态单元素控件不受此条限制

### 审计判据

- 本地 CI 输出 `per-item` / `leak-risk` / `render-path` 三类时，必须逐个判断，不得以「脚本不失败」为由整体放过。
- 能委托就委托；事件不冒泡时，改用会冒泡的等价事件，或交给 CSS 状态。
- `inline` 类内联事件无法委托，沿用既有写法即可。
- `delegated-ok` / `global-once` / `guarded-ok` / `ephemeral` / `ok` 五类已按静态依据排除，不重判。
- 该审计不进入 GitHub Actions：判断需要业务语义，脚本在 `GITHUB_ACTIONS=true` 时跳过，不是漏配。

## P0-2 结论必须先验证并附可复核证据

**任何结论都要先验证再说出口，不许先给结论再回头说"其实我没验证"**

- 说"这是活链路""这个没用""删掉不影响"之前，必须已经查过调用点、跑过验证
- 没查清就说"应该是""大概是""我理解是" —— 等于没验证，照样违规
- 查不动或查不清时，直说"我还没验证"，**不要给一个听起来确定的结论**
- 结论里带上证据：哪个文件哪一行、哪个命令的输出、哪个测试通过
- 用户按结论做决定，错的结论比"不知道"危害大得多

**任何结论、bug 判断、修复效果、回归自测，都必须附可复核证据。**

- 界面、交互、样式、任务列表与可见状态：必须提供能看清关键状态的页面截图
- 后端、CLI、数据结构：可提供命令输出、测试结果、请求响应或截图
- 截图必须来自实际页面或实际运行实例，不得用手绘、文字描述或伪造状态代替
- 自测若改变界面或可见状态，必须提供前后截图
- 没有任何可复核证据的结论，视为未验证，不得作为交付依据

## P0-3 测试数据自己收拾，不许问

**自己为测试造出来的数据（会话、文件、目录、进程），测完当场删掉**

- 绝不问"要不要我删掉" —— 自己拉的自己擦
- 绝不把这件事留到下一轮或收尾时当"待办"报给用户
- 删之前逐条列出删了什么；**只删自己建的那些**，用户的东西一概不碰
- 造测试数据时就用可辨认的前缀（`probe-` / `slim-` / `seq-` 等），便于精确删除
- 清理脚本必须**先列出将要删的每一个名字并核对**；名字对不上就中止整个脚本，不许"过滤一下继续删"
- 禁止用"清空整个目录"式的命令（如 `Get-ChildItem <dir> | Remove-Item`）—— 用户可能正在同一个目录里测试

## P0-4 代码与文档表达

注释不是日记，不是辩护，不是写给作者自己的备忘录。注释只解释代码本身；文档只陈述当前事实与契约。

允许写：

- 不变量
- 边界条件
- 平台或 API 硬要求
- 非显然的实现原因
- 改动会破坏什么

禁止写：

- 与源码无关的规格编号、决策编号、批次标号、阶段号、章节号
- 过程叙述、轮次叙述、历史原因
- 版本、阶段、演进口吻
- 对读者叮嘱、设计辩护、方案对比
- 文件导读、元叙述、待办标记
- 与当前行为矛盾的旧注释
- 对读者讲话或解释性文案
- 任何前身、来源、移植、重构叙事

判据：

- 换一个不了解项目历史的读者来看，这句话是在解释代码，还是在跟他说话。
- 仅在非显然的实现选择写注释。
