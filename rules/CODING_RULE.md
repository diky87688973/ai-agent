# 编码规则

## P0-1 动态列表事件委托

**由 JavaScript 动态创建或重渲染的列表项、卡片、行、按钮，禁止逐个绑定事件监听器**

- 事件必须委托到稳定的顶层容器，例如 `document` 或列表根容器
- 通过 `event.target.closest(selector)` 定位具体元素，再读取 `data-*` 等属性分派行为
- 禁止对每个动态元素执行 `addEventListener(...)`、`onclick = ...` 或其他逐项绑定
- 顶层监听器只能注册一次；重复初始化必须幂等
- 键盘事件同样遵守顶层委托
- 静态单元素控件不受此条限制

## P0-2 结论必须先验证且必须带截图证据

**任何结论都要先验证再说出口，不许先给结论再回头说"其实我没验证"**

- 说"这是活链路""这个没用""删掉不影响"之前，必须已经查过调用点、跑过验证
- 没查清就说"应该是""大概是""我理解是" —— 等于没验证，照样违规
- 查不动或查不清时，直说"我还没验证"，**不要给一个听起来确定的结论**
- 结论里带上证据：哪个文件哪一行、哪个命令的输出、哪个测试通过
- 用户按结论做决定，错的结论比"不知道"危害大得多

**任何结论、bug 判断、修复效果、回归自测，必须附页面截图或可复核的截图路径**

- 界面、任务列表、样式、交互的结论，必须给出能看清关键状态的截图
- 自测必须提供前后状态截图；不能只给文字、日志、测试通过结果或记忆
- 截图必须来自实际页面或实际运行实例，不得用手绘、文字描述或伪造状态代替
- 没有截图证据的结论，视为未验证，不得作为交付依据

## P0-3 测试数据自己收拾，不许问

**自己为测试造出来的数据（会话、文件、目录、进程），测完当场删掉**

- 绝不问"要不要我删掉" —— 自己拉的自己擦
- 绝不把这件事留到下一轮或收尾时当"待办"报给用户
- 删之前逐条列出删了什么；**只删自己建的那些**，用户的东西一概不碰
- 造测试数据时就用可辨认的前缀（`probe-` / `slim-` / `seq-` 等），便于精确删除
- 清理脚本必须**先列出将要删的每一个名字并核对**；名字对不上就中止整个脚本，不许"过滤一下继续删"
- 禁止用"清空整个目录"式的命令（如 `Get-ChildItem <dir> | Remove-Item`）—— 用户可能正在同一个目录里测试

## P0-4 能自己判断的事不要问

**属于我的判断范围、且有明确依据的（死代码该不该删、文档措辞、命名统一、测试怎么写、要不要补测试……），直接做掉，做完汇报**

- 只有**用户的决定**才问：他的数据怎么处理、产品方向、外部账号、不可逆的对外动作
- 把"该我干的"推给用户，等于让用户替我做我的活

## P0-5 代码与文档内容

- 不写与源码无关的内容：不留规格编号、决策编号、批次标号、阶段号、章节号
- 不写工程过程叙述：不写"谁提出的""第几轮发现的""当时代码怎么坏""此前如何"
- 不写版本关系：本工程是第一个版本，不提及任何前身、来源、移植、重构
- 不写叮嘱、不写解释性文案、不写对读者讲话
- 注释只陈述代码本身
- 仅在非显然的实现选择写注释
