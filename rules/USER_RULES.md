# 用户规则

## P0 级约束（不可越过、不可降级）

### P0-1：提交 GitHub 前必须通过准入检查与工程复核

**适用范围**：任何会改变 GitHub 仓库状态的动作 —— `git push`、创建/更新/关闭 PR、创建 issue、修改仓库设置（topics、release 等），以及会被这些动作一并推送上去的本地提交之前。

**强制流程（三步，顺序不可颠倒，任何一步都不得跳过）**：

1. **准入检查**：确认本次改动范围只覆盖任务相关文件；无顺手重排、无顺手重命名；无密钥与真实配置入库；`.gitignore` 已覆盖且 `git ls-files` 里确实不存在；无未说明的静默吞错；新增的超阈值大文件已登记。
2. **工程复核**：按生产级交付准则逐项核对，结论**必须带证据等级**——已观测（跑过、有输出）、强推定（代码与环境都支持但未运行）、未验证（明确留白）。写明：跑了什么、结果如何、没跑什么、为什么没跑。
3. **通过后才提交**：仅当复核结论为「通过」时，才允许执行提交动作。

**禁止项**：

- 禁止以「改动很小」「时间紧」「只是文档」为由跳过复核。
- 禁止把「读过代码觉得对」表述成「已验证通过」。
- 禁止先提交、后补复核说明。
- 复核中发现的问题，必须先修再重新复核，不得带着已知问题提交。

**判定方式**：若无法给出本次复核的证据（命令输出、退出码、测试结果，或明确声明哪些未验证），视为复核未完成，提交一律不允许。

### P0-2：提交说明只用标题加短条目，不写长篇

**标题**：`type: 一句话说清做了什么`。type 用 `feat` / `fix` / `refactor` / `docs` / `test` / `chore`。不带句号，不堆定语，不超过 30 字。

**正文**：只写 `- ` 开头的短条目。每条以动词开头，说清干了什么：增加什么、修复什么、调整什么、优化什么。一行动作一个事实，四到六条为宜。末条可写「同步测试、文档」这类收尾项。

**正例**（三种场景各一）：

修复问题：

```
fix: 头像上传失败时不再静默
- 增加超限提示，报出实际大小与上限
- 修复重试时丢图
- 保留失败时已填内容
- 补上传失败与重试用例
```

新增功能：

```
feat: 图片预览支持 1:1 实际像素
- 改为默认按实际像素打开
- 增加切回铺满的开关
- 支持小于窗口时居中、大于时可滚动
- 接入工具详情里的图片
- 补预览与点击用例
```

调整优化：

```
refactor: 搜索默认不再跳过项目临时目录
- 收窄默认名单，只留版本库与字节码缓存
- 移除对项目临时目录的默认跳过
- 新增 exclude，要排什么由调用方点名
- 回执报出实际跳过目录数
- 同步测试与文档
```

**禁止项**：

- 禁止把「问题 / 改法 / 验证 / 证据」立成小标题再分段作文。
- 禁止条目写成描述句（「上传超限时报出大小」），必以动词开头（「增加超限提示」）。
- 禁止在提交说明里写推导过程、原理讲解、门禁步数、用例数量。这些内容归入复盘或对话正文，不进提交说明。
- 禁止一句里塞多个分句、堆定语。一条只讲一件事。
- 禁止以「为了兼容某批改动所以合并提交」这类过程叙述充当正文。

**判定方式**：正文若出现段落文字（非 `- ` 开头的成句），或长度超过六条，或条目不以动词开头，即为不合格，重写后再提交。
