# 生产级交付准则

> 用途：新项目从第 0 天起就照此搭骨架；评审时照此挑问题。
> 每条准则都给出**它防的失败模式**。看不懂某条为什么存在时，先看失败模式——若你的场景确实不适用，按 0.5 在 `docs/applicability.md` 里显式申报，不要默默跳过。

---

## 〇、怎么用这份手册

### 0.1 效力等级

| 标记 | 含义 | 违反代价 |
|---|---|---|
| `MUST` | 不变量。违反即视为缺陷，合并前必须修 | 阻塞合并 |
| `SHOULD` | 默认做法。偏离需在 PR 或 ADR 中写一句理由 | 评审可能打回 |
| `MAY` | 可选。团队自定，但一旦定下就要一致 | 无 |

### 0.2 验证方式

| 标记 | 含义 |
|---|---|
| `机` | 可被脚本/CI 判定。应写进门禁，而不是靠人记 |
| `审` | 只能靠评审判断。评审清单里必须有对应条目 |
| `测` | 靠测试锁住。缺测试等于这条不存在 |

**核心原则：凡是能写成 `机` 的，就不要写成 `审`。** 靠人记的规范会在第三次迭代后失效；靠脚本的规范会一直有效，并且会自己抓出"以为改了其实没改"。

### 0.3 判据从哪来

本手册的阈值与失败模式，来自真实生产代码库中被反复观察到的缺陷形态：上帝包、分层倒挂、错误被静默丢弃、门禁子串匹配被改名绕过、CI 清单与人脑清单漂移、覆盖率口径漏掉新拆模块、无凭据即跳过导致门禁永久红。写法上刻意区分"这条是通识"与"这条是某类系统的特产"。

### 0.4 适用域

同一批准则要同时服务常驻服务、纯库、命令行工具与桌面应用，但四者的失败模式不同。
每条准则默认适用于**全部**适用域；只有明确标注时才收窄：

| 标记 | 收窄到 | 理由 |
|---|---|---|
| `[服务]` | 常驻进程 / 有部署与运维面的系统 | 这类系统有启动、降级、关停、回滚与对外鉴权，纯库没有这些阶段 |
| `[库]` | 被他人 import 的发布物 | 这类系统没有进程边界，但有 API 兼容性、导入副作用与调用方不可控的约束 |

标注必须落在准则条目上，不是落在章节上：同一章里可能既有通识也有特产。

适用域不是豁免。标 `[服务]` 的条目对纯库仍然成立，只是**风险承担者换了人**——
库没有 `/health`，但"静默降级不可见"这条依然要有人管（通常是返回错误码或指标）。
连"谁承担这个风险"都答不出来时，说明该条目在本次范围内真的不需要，此时走 0.5，
而不是把条目删掉或改成"不适用"了事。

### 0.5 不适用必须可查，且必须双向

"不适用 + 原因"不能只写在人脑或 PR 描述里——那样它在第二次迭代就消失了。

项目根下维护一份 `docs/applicability.md`，每行一条：

| 准则 | 申报 | 原因 | 风险由谁承担 |
|---|---|---|---|
| `S8` | 不适用 | 无对外服务，全部调用在同一用户下 | 无（不存在认证边界） |
| `V4` | 不适用 | 不发布镜像与迁移 | 无 |

约束：

1. 只能申报 `MUST` / `SHOULD` 条目，且必须写"风险由谁承担"，不能只写"不需要"。
2. 申报与门禁清单**双向比对**：清单里有而申报里没有的条目，必须按标准执行；
   申报里出现清单中不存在的编号，视为过期申报并报错（`机`）。
3. 申报总数与 `N/A` 占比要在 CI 输出里可见。占比持续上升是"标准被逐条掏空"的信号，
   比单条违规更值得警惕。
4. 新条目加入手册时，申报表不会自动获得一条豁免——缺省即适用。

## 一、交付纪律（先于一切技术规范）

**G1｜先分类，再动手** · `MUST` · `审`

面对一个请求，先判定属于哪类：解释 / 只读审查 / 小改 / 大改 / 架构调整。**只读类请求默认不写盘**。

> 失败模式：把"帮我看看这段代码有没有问题"当成"帮我改好"，产出用户没要的 diff，把一次咨询变成一次事故面。

**G2｜改前必读，不猜路径与行号** · `MUST` · `测`

修改任何文件前先读到当前内容；修改后若同文件还要再改，先复核落盘后的实际状态。

> 失败模式：基于记忆或基于"通用最佳实践"改一片代码，改动落在错误位置，或在已被改过的行号上打补丁，产生静默损坏。

**G3｜最小可行改动** · `MUST` · `审`

只改完成任务所必需的部分。不顺手重排 import、不顺手统一引号、不顺手升级依赖。

> 失败模式：一次"顺便格式化"让 diff 从 20 行涨到 800 行，真正的逻辑改动被淹在噪声里，评审失效、`git blame` 失效、回滚粒度失效。

**G4｜先验证，再声称完成** · `MUST` · `审`

能跑的必须亲自跑。跑不了（缺凭据/缺环境/缺平台）必须**明确说出没验证什么**，并说明结论的证据等级。

> 失败模式："应该没问题"上线后在第一条真实路径上崩。更坏的是它看起来像已验证。

**G5｜结论要带证据等级** · `SHOULD` · `审`

区分三档并在结论里标明：

- **已观测**——我执行了，有输出/退出码；
- **强推定**——代码路径 + 环境事实都支持，但未运行验证；
- **未验证**——没看/没跑，明确留白。

> 失败模式：把"读代码觉得对"说成"已测试通过"，把推定当事实，后续决策全建立在错误置信度上。

**G6｜不做未授权的写操作** · `MUST` · `审`

不替用户 commit / push / 改远程 / 删数据 / 动生产配置，除非明确要求。

## 二、架构与模块边界

**A1｜单包体量阈值** · `MUST` · `机`

一个**扁平**包（无子包）下的手写代码达到 **300 文件**或 **3 万行**，就必须按子域拆子包。

> 失败模式：文件名前缀（`openai_gateway_*`、`channel_monitor*`）替人脑维持了"子域"的幻觉——但编译器和门禁看不见这些前缀。于是：改一个子域等于在 25 万行里改；想加"禁止跨子域调用"的约束根本无法表达；任何细分都要先做一次大规模搬文件，而搬文件在几百个测试文件的前提下成本极高，于是永远不拆。

**A2｜依赖方向双向约束** · `MUST` · `机`

分层规则必须**双向**写进门禁，且必须同时覆盖**层内**。只禁住层间一个方向等于没禁。

> 失败模式：只写"业务层不得依赖持久层"，没写"持久层不得依赖业务层"。后者悄悄发生了 111 个文件、用到 554 个业务包符号（实体、错误值、枚举全在里面）。结果：文档里的分层图是假的，持久层无法独立测试，业务包无法独立演进。**分层只存在于目录名里。**
>
> 第二种失败模式更隐蔽：层间方向全对，但**同层两个模块互引**。单看每个 import 都在允许方向内，逐条检查永远通过；实际后果是该层无法独立测试、无法按模块拆包，且 import 顺序会变成隐式契约。判据是把依赖图跑一遍强连通分量（SCC），把每个大于 1 个节点的环都报出来——成对互引只是其中一种，三角环同样要报。
>
> 第三种：门禁按"目录名"分层，而重构时目录搬了、规则表没跟着搬。分层规则必须以**包路径**为键，且门禁自带的负向测试要覆盖"目录搬走后规则失效"这一形态。

**A3｜领域模型要有实体归属** · `SHOULD` · `审`

若存在 `domain` / `model` 目录，但其中的代码只有几百行的空壳，而领域实体实际住在业务编排包里——说明你没有领域层，只有分层的**命名**。

> 判据：随机抽 3 个核心实体，看它们的类型定义在哪个包。答案若是"编排包"，则为 `A3` 违规。

**A4｜扩展方式是加模块，不是改核心** · `MUST` · `审`

新增一个同类能力（新适配器、新工具、新数据源、新支付渠道），应当**只新增文件 + 一处注册**。若需要改 3 个以上已有文件，说明扩展点没设计出来。

> 判据：让一个没参与过该项目的人试着加一个假想能力，记录他被迫修改的已有文件数。这个数字就是架构的真实扩展成本。

**A5｜装配点集中且可读** · `SHOULD` · `审`

依赖注入/装配应集中在一处，且该处的复杂度随服务数量线性增长而非爆炸。

> 失败模式：清理函数把约 50 个服务的 `Stop()` 作为 50 个入参收进一个签名。每加一个后台任务都要动这个签名，且 50 个服务的关停顺序无人能审。**装配点成了变更的必经收口。**

**A6｜内核不知道插件名** · `MUST` · `机`

core / 核心层不得出现具体插件、具体业务方的标识符。

> 理由：一旦内核点名插件，"可选"就成了假的——插件改名要动内核，插件缺失要改内核分支。检查方式：扫描 core 目录，命中插件目录名即违规（注意词边界，别把 `atts` 误判成 `tts`）。

**A7｜边界要能被机器证明** · `SHOULD` · `机`

分层的价值来自"违反会被拦"，不是"文档里写了"。每条分层规则都应有一条对应的可执行检查。

> 反面样本：`depguard` 里真实生效的规则（`service` 不 import `repository`，实测 0 处违反）是有效的；同一份配置里没有表达的反方向，就演化了 111 处倒挂。**同一份文件里，写了的规则守住了，没写的规则丢了。**

## 三、契约与数据模型

**B1｜只读视图必须是真不可变** · `MUST` · `测`

对外暴露内部集合时，返回的结构必须在**所有层级**上都不可变，而不只是顶层容器不可追加。

三种做法只有第三种成立：

1. 返回列表并宣称"只读" —— 调用方仍可 `view.events.append(x)`；
2. 只把顶层换成 `tuple` / frozen 类 —— 挡住了 `append` / `clear`，但 `view.events[0]["x"] = 1`
   仍然改到了内部状态；字段是 `List` / `Dict` 的 frozen 类同理；
3. 顶层不可加 + 元素不可改（元素本身 frozen、或返回**深拷贝**、或元素是同值不共享的
   新构造的不可变记录）。三者任一即可，但必须能说出是哪一种。

判据：拿到返回值后，把里面任意一层元素改一下，再读内部状态；内部读到变化即为违规。

> 失败模式：返回列表并宣称"只读"。调用方仍可 `view.events.append(x)` 造出**内部可见、观察面不可见**的秘密状态；`clear()` 甚至能清空整段历史。这类 bug 表现为"日志里没有但行为里有"，排查成本极高。
> 更隐蔽的版本是"顶层 tuple、元素共享"：`append` 被挡住了，评审也过了，但下游只改了一个字段，事实源就跟着变了——而改动点离事故点隔着三层调用。
> 代价可接受：每次访问 O(n)。当元素是百量级、且下游本来就要全量遍历时，这点代价换"真不可变"是划算的；元素上万时改用只读代理或按需构造，不要退回可变共享。

**B2｜契约稳定、最小、可测** · `SHOULD` · `审`

接口只暴露调用方真正需要的；泄露实现细节（内部字段名、内部序号、私有路径）会把实现变成冻结契约。

**B3｜避免 `Any` 泛滥** · `SHOULD` · `审`

端口/接口层出现大量 `Any` 时，契约退化成"什么都能传"，编译期与测试都失去检查力。至少给核心数据结构定义 `dataclass`/`TypedDict`。

**B4｜一物一名，禁止同名不同物** · `MUST` · `审`

同一个标识符不得在不同语境下指两件事。

> 失败模式：`confirm_id` 在一个语境里是"预览快照 ID"，在另一个语境里是"宿主确认单 ID"。两者都是"确认"，都出现在同一段对话里，人和模型都会串。这类歧义**不报错、只把人带偏**，功能测试抓不到，只能靠文案断言或改名。

**B5｜"忠实折叠"与"请求修补"分离** · `SHOULD` · `测`

从事实派生出下游结构时，若存在"事实真相"与"下游硬约束"不一致的情况，应拆成两个函数：

- 折叠：忠实反映事实（悬空就是悬空）；
- 修补：满足下游硬约束（补齐缺口），且应是**纯函数**、可单测。

> 失败模式：把修补混进折叠。此处具体后果是：一条悬空的 `assistant(tool_calls)` 一旦进入历史，此后每个请求都带着它，会话永久打不开。修补用"说明性占位"而非拒绝，因为拒绝会把用户卡在他无法理解的错误上。

**B6｜契约版本化** · `SHOULD` · `审`

跨进程/对外契约（API、事件格式、落盘格式）变更时，要有版本字段 + 兼容窗口，而不是就地改。

## 四、控制流与数据流

**C1｜控制流走返回值，数据流走事件** · `SHOULD` · `审`

若采用事件/流式模型：返回值只携带控制信号（继续/停止/终止），业务数据一律走事件通道。反向做法（把数据塞进返回值、把控制藏在事件里）会让状态来源分裂。

**C2｜终态必须穷尽且显式** · `MUST` · `测`

一个回合/任务/请求的所有终态必须被显式枚举并各自带标记。

> 失败模式：只区分 `paused` 与"完成"。用户主动停止、护栏触顶、正常完成三者混同 → **触顶被 UI 报成"正常完成"**，用户以为做完了。
> 正确做法：`paused` / `halted` / `stopped` / `abandoned` 各自独立，且每条中止路径都显式带全三种布尔标记。

**C3｜流式必须真流式** · `MUST` · `测`

流式接口要"产出即让出"。任何"先收集成列表再转发"的写法会让流式名存实亡。

> 判据：测量首字节时间（TTFT）。若与总时长同阶，说明是伪流式。

**C4｜状态归属单一** · `MUST` · `机`/`审`

每份可变状态只能有一个权威持有者。禁止"注册表里一份、对象属性里一份"的双份状态。

> 失败模式：两份状态在正常路径上同步良好，在异常路径上分叉。之后所有"为什么这里有、那里没有"的问题都无解。

**C5｜不用 `assert` 做控制流** · `MUST` · `机`

`assert` 只可用于内部不变量自检，**不可**用于表达"必然成立所以直接取属性"。

> 失败模式：`assert result is not None` 之后紧跟 `result.terminal`。在 `python -O` / `PYTHONOPTIMIZE=1` 下 assert 被剥离，程序不是给出可读的契约错误，而是 `AttributeError: 'NoneType'`。
> 替代：`if x is None: raise RuntimeError("模块链契约违例：未产出 result")`。

**C6｜取消优先于续跑** · `MUST` · `测`

若存在"结束后自动续跑/重试/进入下一轮"的逻辑，**必须先判取消位再判续跑条件**。

> 失败模式：续跑判定只看业务状态（目标是否 active），而取消位一经置位无人清除 → "起新一轮 → 开头立刻被取消 → 又续跑"无限转，CPU 打满、事件流被灌爆，界面上的"停止"等于没按。

## 五、错误处理与失败路径

**E1｜禁止丢弃错误** · `MUST` · `机`

以下形态一律视为缺陷：

```go
_ = repo.SetError(ctx, id, msg)   // 丢弃了写库错误
v, _ := strconv.Atoi(s)           // 丢弃了解析错误且无默认值语义
```

```python
except Exception:
    pass                          // 静默吞掉
```

> 失败模式：状态写入失败无痕。调度器下一轮仍按旧状态选中该账号；账单/配额状态漂移；**而且没有任何日志**。这类缺陷不进错误率、不触发告警，只在下游表现为"数据不对"。
> 例外：`_ = resp.Body.Close()`、`_ = w.WriteField(...)` 这类确实无需检查的，逐点标注理由（`//nolint:errcheck // 关闭失败不影响已有响应`），**不要**通过全局关闭检查规则来放过它们。

**E2｜错误检查规则不得全局关停** · `MUST` · `审`

"允许丢弃错误"的配置（如 `check-blank: false`）与"整族安全规则的全局豁免"（如同时豁免路径穿越、文件权限、SQL 拼接、硬编码凭据）都应避免。要豁免就**逐点**豁免并写信任边界。

> 失败模式：一个 `gosec.excludes` 列表里同时豁免了 `G304`（路径来自变量）、`G306`（文件权限过宽）、`G201/G202`（SQL 拼接）。对一个能读写配置、导出文件的网关服务，这是实质攻击面，而门禁不再提醒。

**E2a｜按类豁免只在四条同时成立时可用** · `SHOULD` · `审`/`机`

检查器有时必须区分"吞掉了"和"吞掉了但有正当理由"，而逐点注释在上百处会退化成噪音。
此时允许**按类豁免**（一张"惯用法表"），但它必须同时满足：

1. **一处登记**：整类只登记一条正则/一条规则，散落在各文件的注释不算；
2. **每条带判据**：为什么这一类可以吞，必须写在登记处，不写在调用点；
3. **命中数可见且单调下降**：CI 输出必须报出"按类豁免命中 N 处"，
   `N` 只许降不许升；新增需求走逐点豁免，不许往表里加新类；
4. **抽样可审**：`N` 超过约 50 时必须能列出命中位置，且评审每年至少抽查一次。

任一条不成立，就退回逐点豁免。**"有这张表"不等于"这张表是对的"**——一张表覆盖
几百处时，它已经变成事实上的全局关停，只是换了名字。

> 失败模式：检查器为了变绿先加了 3 条惯用法，一年后变成 12 条、覆盖 119 处。
> 每一条单独看都合理，合起来等于"静默吞掉基本不检查"。而因为门禁是绿的，
> 没有任何人再看它。

**E3｜失败必须留痕到可查询面** · `MUST` · `测`

任何被刻意吞掉的异常，必须至少写一条结构化留痕（错误码 + 关键上下文）。**"刻意吞掉"与"静默吞掉"的区别就在于有没有留痕。**

> 失败模式：唯一的事件出口抛异常后被 `except: pass` 吞掉 → 界面永久"思考中"，日志里什么都没有。而同文件其他位置都走 `report_error`，唯独这里没有——症状与原因之间没有任何线索。

**E4｜区分"业务失败"与"不变量破坏"** · `SHOULD` · `审`

- 业务失败（校验不过、资源不存在、配额不足）：返回结构化结果，不要 `raise` 到无法恢复的层面；
- 不变量破坏（不该发生的状态）：直接抛，并带上足够定位的上下文。

**E5｜退出码要能区分"跳过"与"失败"** · `SHOULD` · `机`

自动化脚本应区分：`0` 成功、非 0 失败、**独立码**表示"环境不满足（跳过）"。

> 失败模式：把"缺凭据"和"跑了但没通过"混为一谈，CI 常红 → 没人再看它 → 真正的失败被忽略。

**E6｜资源生命周期用作用域管理** · `MUST` · `审`

文件、连接、事务、锁、临时目录一律用语言级作用域机制（`with` / `defer` / RAII）。事务回滚失败可以只记日志，但**提交失败必须处理**。

## 六、并发与状态

**K1｜共享可变状态必须有明确归属与同步** · `MUST` · `机`/`测`

进程内共享可变状态：明确唯一持有者 + 明确同步原语。禁止"某模块自己缓存一份"。

**K2｜关停顺序按数据流反序** · `MUST` · `审` · `[服务]`

关闭顺序必须是：停止接收新输入 → 停止**生产者** → 停止**消费者** → 关基础设施。

> 失败模式：把约 50 个服务的 `Stop()` 全塞进一个并发批次并行执行，只把数据库/缓存放最后。关停窗口内，usage 记录的生产者可能向已停止的消费者投递 → 记录丢失或错误刷屏。
> 纯库没有关停阶段，但"释放顺序"仍在：全局注册表、缓存、线程池若在模块层级持有资源，需在文档里说明由调用方按什么顺序释放，或干脆不持有。

**K3｜长任务需要心跳，但不能代替超时** · `SHOULD` · `测` · `[服务]`

"是否还在跑"这类判断，若靠心跳 + TTL，心跳间隔必须显著小于 TTL（如 60s vs 900s）。

> 失败模式：一次 `ping -n 120` 式的长工具调用期间没有心跳，被判"已结束"，用户那边的"停止"键消失。

**K4｜并发安全必须有检测手段** · `MUST` · `机`

凡涉及共享可变状态，CI 必须至少有一个**能发现数据竞争**的作业，且该作业必须在 CI 里跑，不是"本机能跑"。

手段按运行时选择，并在项目内写明选了哪种：

| 运行时 | 可用的手段 |
|---|---|
| Go | `go test -race` |
| C/C++/Rust | TSAN / `loom` / `miri` |
| JVM | jcstress、`-XX:+UnlockDiagnosticVMOptions` 压力作业 |
| CPython | `-X dev` + `PYTHONDEVMODE=1` 跑并发测试、`threading` 争用用例、`-X gil=0`（free-threading 版本）；**有 GIL 不等于没有竞态**：GIL 只保证单条字节码原子，跨多步的检查-后写入照样撕裂 |
| Node/浏览器 | `--experimental-*` 并发用例 + 事件循环饥饿测试 |

没有任何自动化手段可用时，退化为"显式并发压测用例 + 人工评审清单"，但必须在
`docs/applicability.md` 里申报，不能默默不做。

> 失败模式：几十个互斥锁、上百处 `go func`、数百处原子操作，但 CI 从不带 `-race`。竞态只在生产暴露，且表现为"偶发计数错误"——最难归因的一类 bug。
> 另一种失败模式：标准只举了 Go 的例子，于是非 Go 项目把这条读成"我们没有 -race，所以不适用"。**判据是"有没有检测手段"，不是"有没有那个命令"。**

**K5｜单实例假设要写出来** · `MUST` · `审`

若系统假设"同一时刻只有一个进程/一个会话在跑"，必须写在文档与代码注释里。

> 无并发风险的局部模块，要说明"适用范围窄"，而不是因此拿高分。范围窄是事实，不是优点。

## 七、持久化与数据完整性

**P1｜追加写必须整批原子** · `MUST` · `测`

批量追加落盘：**记下追加前偏移 → 追加 → 失败则 `truncate` 回滚**。要么整批可见，要么整批不可见。

> 失败模式：逐行写，半写失败后重试整批 → 磁盘出现重复行与重复坐标。后续"重放历史"直接坏掉。
> 不采用"整文件重写 + `os.replace`"的理由要写清：原子但昂贵且随文件长度二次增长（实测 2.33MB 文件单次 append 14.3ms vs 追加 0.133ms）。当硬要求只是"失败重试不产生重复行"时，偏移+回滚更划算。

**P2｜重试队列归属单一** · `MUST` · `审`

落盘失败的重试只能由**一个**组件负责。上层不得"把批次放回自己的缓冲再写一遍"。

> 失败模式：上层补偿 + 下层重试队列同时存在 → 同一批事实被渲染两次、坐标重新分配 → 重复行。
> 正确做法：下层入待重试队列并抛出；上层只负责**留痕**（"观察面已渲染但未落盘"），不重试。

**P3｜落盘粒度按"最小可丢单元"** · `MUST` · `测`

按阶段/批次增量落盘，而不是攒到任务结束一次性写。

> 失败模式：攒到回合末写。中途异常 → 界面已渲染完整对话，存储里一个字都没有、刷新即消失，**连用户的第一句话一起丢**。按趟落盘则最多丢当前一趟。

**P4｜迁移必须有回滚策略或显式声明仅前滚** · `MUST` · `审` · `[服务]`

> 失败模式：319 个迁移文件里含 `down` 的只有 1 个。破坏性变更（删列/改类型）不可逆，只能恢复备份——而备份是否可恢复从未验证。
> 纯库不发布迁移，但"落盘格式变更"同样适用：可选字段只前滚、缺省按无处理、不要求旧数据迁移，
> 这句话必须写进文档；"我们只前滚"是有意识的取舍，不是没想过。

**P5｜破坏性操作要有前后对照** · `SHOULD` · `测`

删除/大改要在写后报告"改了多少、删了什么"。大删除应触发红灯提醒。

**P6｜落盘格式的键名不得硬编码到读取方** · `SHOULD` · `审`

读取方应复用写入方导出的键常量。硬编码字符串会随键名改动静默失配。

> 失败模式：会话标题读取方硬编码 `"input_claimed"`，写入方改了键名 → 标题静默退化为空，不报错。

## 八、安全与信任边界

**S1｜输入校验在信任边界处，不在使用处** · `MUST` · `机`

路径、命令、SQL、模板、反序列化：在**进入系统的那一步**校验，不依赖下游各自小心。

**S2｜路径校验用"解析后比对"** · `MUST` · `测`

```python
Path(root).resolve().relative_to(Path(base).resolve())   # 后者是前者的祖先
```

不要用字符串前缀判断（`..`、符号链接、Windows 盘符都能绕过）。

**S3｜命令执行避免 shell 拼接** · `MUST` · `机`

参数以列表传递，不拼 shell 字符串。必须拼时，白名单 + 拒绝字符集。

**S4｜信任模型写成"能指望 / 不能指望"两列** · `MUST` · `审`

任何"信任同级代码"的设计（插件、扩展、脚本），必须明确写出：

| 能指望 | 不能指望 |
|---|---|
| 约定与命名空间约束 | 恶意代码被运行时拦住 |
| 装载期记录来源与摘要 | 子进程隔离或权限降级 |

> 失败模式：文档只写"插件与本机代码同等信任"，读者以为已经做了校验。实际上只**记录**了 sha256，没有比对、没有拒绝分支。诚实的两列表能让读者立刻分清"记录"与"校验"。

**S5｜"记录"与"校验"必须用词区分** · `MUST` · `审`

日志里写 `sha256=...` 而不写 `verified=yes/no`，等于给人"已校验"的错觉。**未校验就别说校验。**

**S6｜秘密不进版本库** · `MUST` · `机`

`.gitignore` 覆盖真实配置与密钥；仓库内只放 `.example`；CI 通过 secrets 注入。

> 同时注意：`.gitignore` 生效 ≠ 历史上没提交过。要额外确认 `git ls-files` 里确实不存在。
> 第三个坑：同一份配置同时存在"真实文件"与"`.example`"，而**没有门禁比对两者的键集合**。
> 于是 `.example` 慢慢少了两个键、多了三个键，照它配出来的环境起不来，且没人知道该照谁。
> `.example` 与解析器实际读取的键集合必须双向一致（`T4`），这条对库同样成立。

**S7｜安全默认** · `SHOULD` · `审`

新增的收紧开关，默认值应为"收紧"，并提供显式逃生阀（`=0`）。

> 若因兼容性必须默认关闭，在文档里写明"缺省关闭（兼容 X）"——这是有意识的取舍，不是疏漏。

**S8｜认证/授权边界要可辨认** · `MUST` · `审` · `[服务]`

中间件目录应能一眼看出哪些是鉴权、哪些是限流、哪些是审计；每条受保护路由的鉴权归属应可查。

> 纯库没有对外路由，但"谁能调到我"同样要能答：公开 API 与内部 API 的边界在哪、
> 哪些函数假定调用方已校验入参（`S1` 的信任边界），必须写在文档里而不是靠命名暗示。

## 九、配置与秘密管理

**T1｜配置读取要能定位错误** · `MUST` · `测`

配置文件缺失/损坏/编码异常时，错误信息必须指出"哪个文件、什么原因"。

> 失败模式：Windows 记事本另存写了 UTF-8 BOM，`configparser` 抛 `MissingSectionHeaderError: File contains no section headers`——错误信息完全指不到"配置被加了 BOM"。修法：用 `utf-8-sig` 读取（对无 BOM 文件行为一致）。

**T2｜环境变量优先于文件** · `SHOULD` · `审`

便于容器化与 CI 覆盖。提供 `AI_AGENT_X=1/0/true/false/on/off` 的完整解析。

**T3｜缺省值要写进文档** · `SHOULD` · `审`

配置项的缺省值、单位、取值范围、以及"不设置时的行为"必须可查。

**T4｜配置漂移要有检查** · `SHOULD` · `机`

`.example` 与实际读取的键集合必须**双向**一致，并进门禁：

1. 缺的报（`.example` 漏了键 → 照它配出来的环境起不来）；
2. 多的报（`.example` 留了已废弃的键 → 下一个人以为它还有效）；
3. 解析器里读了但没在任何 `.example` 出现的键，同样报。

新增配置项必须同时更新 `.example` 与文档。只靠"记得同步"必然漂移，
而且漂移的表现是"照文档配不通"，排查成本远高于一条门禁。

## 十、代码整洁与可读性

**R1｜复杂度热点阈值** · `SHOULD` · `机`

- 单文件 > 800 行：需要一句拆分理由，或进入待拆清单；
- 单函数 > 80 行：同上；
- 单文件 > 40 个函数：通常是"多个关注点挤在一起"。

> 阈值本身不是目的。目的是：让"这个文件很大"成为**被看见的事实**，而不是三个月后的意外。注意分布——若中位数是 232 行而少数文件是 3000+ 行，说明不是普遍臃肿，而是少数失控，这是可修的。
> "登记"必须有落点：一份 `docs/complexity.md`（或等价清单）列出超阈值文件与拆分理由，
> 并由一条门禁比对"实际超阈值的文件集合 ↔ 清单"。没有落点的阈值等于没有阈值——
> 第一次超标的文件不会被记录，第一百个也不会。

**R2｜注释解释"为什么"，不复述"做什么"** · `MUST` · `审`

好注释长这样：

```python
# 先清再写：写失败也不重复写已写的
batch = list(self._turn_events)
self._turn_events.clear()
```

**R3｜注释里不放过程叙述** · `SHOULD` · `机`

不写"谁在第几轮发现的""当时代码怎么坏的"。这类内容应进 commit message 或 ADR。代码注释只留**当下仍然成立**的约束与理由。

**R4｜日志出口统一** · `SHOULD` · `审`

不要一半走结构化日志、一半 `print(..., file=sys.stderr)`。若确实需要 stderr 作为运维面，就在文档里声明这一点。

**R5｜删掉死代码，不留兼容坟场** · `MUST` · `审`

已删除模块的转发层、别名层、`_v2` 兼容层一律不留。

> 失败模式：为已删除的旧入口再堆一层转发，于是"新代码"与"旧名字"并存，两年后没人知道哪个是活的。

**R6｜目录可导航** · `SHOULD` · `审`

判据：新人能否在不问人的情况下 60 秒内找到"鉴权在哪""落盘在哪""重试逻辑在哪"。

## 十一、测试策略

**X1｜测试分层且各有职责** · `MUST` · `机`

| 层 | 锁什么 | 何时跑 |
|---|---|---|
| 单元 | 纯函数、状态机、契约 | 每次提交 |
| 集成 | 真实依赖（DB/文件/HTTP mock）的交界 | 每次 PR |
| 端到端 | 用户可见的关键路径 | 每次 PR 或 nightly |
| 契约 | 不变量（依赖方向、格式、门禁自身） | 每次提交 |

**X2｜负向测试：证明门禁抓得住** · `MUST` · `测`

每一条"禁止 X"的门禁，都要有"确实做了 X 但换了写法"的测试，证明它抓得住。数量按门禁类型分级，不搞递归：

| 门禁类型 | 至少所需负例 | 正例 |
|---|---|---|
| 子串/正则匹配 | 4（改名、别名、拼接、注释里出现） | 1（注释里提到禁用词不误伤） |
| AST / 符号级 | 9（属性访问、导入别名、tuple 解包、关键字参数、属性赋值、`getattr` 动态取、`__dict__` 写入、字符串键访问、同义 API） | 1 |
| 数据/清单比对 | 3（缺、多、改） | 1 |
| 行为/覆盖率类 | 2（该红时红、该绿时绿） | 1 |

**终止条件**：不需要"门禁测试的门禁"。整条链条的底部只有一条需要自举——
"检查清单一致性"（`Y3`）。除此之外，任何"为了证明负例有效而新增的元门禁"
都是递归，直接拒绝。

> 失败模式：门禁靠子串匹配 `"preview_tools="`。开发者把变量改名或改用元组解包，门禁显示"通过"，而约束已被绕过。**假阴性比没有门禁更危险**，因为它提供虚假信心。
> 正确做法：AST/符号级判定，并写 9 个负例（属性访问、导入别名、tuple 解包、关键字参数、属性赋值…）+ 1 个正例（注释里提到禁用词不得误伤）。
> 负例必须**真的会失败**：把门禁判定逻辑临时改坏（或在测试里传一个必然违规的假样本），
> 断言它报错。只断言"合规样本通过"是正向测试，一个恒返回 `[]` 的检查器也能过。

**X3｜失败路径要被测试覆盖** · `MUST` · `测`

正常路径的测试只证明"能跑"。必须显式构造：磁盘满、端口占用、语法错、上游返回畸形、并发取消、超时。

> 判据：看测试输出的 stderr。如果全是安静的，说明只测了 happy path；如果能看到 `simulated disk full`、`端口已占用`、`plugin.py 未定义可调用的 register(ctx)` 这类痕迹，说明真的在打错误分支。

**X4｜测试要锁不变量，不只锁行为** · `SHOULD` · `审`

行为测试覆盖"这个输入给这个输出"；不变量测试覆盖"依赖方向不成立""跨层不得用私有名""门控不得有旁路"。后者才是防止架构腐蚀的东西。

**X5｜覆盖率必须由 CI 产出，口径必须覆盖新增模块** · `MUST` · `机`

两条都要：

1. **有作业**：覆盖率是 CI 里的一个步骤，失败会红。手工在本地跑出来的 `.coverage`
   文件不算——它不阻断任何东西，也不会有人看。
2. **口径完整**：统计目录必须包含所有手写代码（含新拆出的模块、插件、脚本），
   排除项要逐条写理由。用配置文件声明口径，而不是在命令行里临时加 `--include`。

> 失败模式：覆盖率只统计 `core`/`mechanisms`。新拆分出来的三个 shell 模块（约 1600 行）**不在统计范围**——恰恰是边界还在流动、最需要守护的地方没有下限。
> 第二种失败模式：口径是完整的，但**没有任何作业去跑它**。仓库里躺着一个 `.coverage`，
> 门禁清单里没有 coverage 这一项，于是"我们有覆盖率"和"我们守覆盖率"是两件事。

**X6｜覆盖率只增不减** · `SHOULD` · `机`

设下限并在 PR 中维持。注意总分会掩盖局部：85% 的 TOTAL 下面可能是某个模块 29%。

> 下限要按**口径里的每个顶层包**分别设，而不是只设一个总数——总分掩盖局部是它的常态，
> 不是意外。

**X7｜skip 必须显式白名单** · `MUST` · `机`

允许跳过的用例/脚本要列白名单，白名单外一律失败；白名单长度本身也要有上限，防止静默膨胀。

> 失败模式：只统计"跳过 3 个不算失败"。半年后跳过了 6 个，没人知道哪 3 个是新增的。
> 判据：**这条上限本身必须能被触发**。写成 `MAX = len(白名单)` 再比较
> `len(去重后的实际跳过) > MAX`，在"先去重、先判非白名单"之后永远为假——
> 门禁看起来在，实际是一条恒真的断言。上限要写成独立常数，并用一条负例证明它会红。

**X8｜测试不得污染工程目录** · `MUST` · `机`

数据根指向临时目录；CI 前后比对工程目录的新增文件，非 0 即失败。

## 十二、CI 与质量门禁

**Y1｜清单单一事实源 + 双向漂移检查** · `MUST` · `机`

"要跑哪些检查"只能有一份清单。CI 配置与本地脚本都从它生成或对它校验，且校验必须**双向**：缺的报、多的也报。

> 失败模式：`ci.yml` 有 9 步，`scripts/ci.py` 有 10 步，多出来的那一步恰好是最强的架构门禁。两份清单各自演进，人只会跑其中之一。**纸面纪律与执行纪律分家。**

**Y2｜门禁顺序按"错了后面不值得看"排** · `SHOULD` · `机`

依赖方向 → 架构洁癖 → 静态检查 → 文档/注册表一致性 → 单测 → 验收（最慢的放最后）。

**Y3｜门禁要自举** · `SHOULD` · `机`

"检查清单一致性"的脚本本身必须在清单里。否则它可以被悄悄删掉。

**Y4｜CI 必须能绿** · `MUST` · `机`

任何"在干净 clone 上必然失败"的门禁都是负资产。

> 失败模式：skip 预算设为 0，而某个验收脚本在缺凭据时返回"跳过"。干净环境永远缺凭据 → 该步必然失败 → 长期红 → 所有人学会忽略红色。
> 正确做法：该验收进白名单（并写明"仅缺凭据"），白名单外一律失败。

**Y5｜依赖必须可复现** · `MUST` · `机`

锁文件（`go.sum` / `pnpm-lock.yaml` / `constraints.txt`）+ 版本矩阵。

> 失败模式：依赖只写下界（`Pillow>=10`）。同一提交在不同时间构建出不同依赖。更隐蔽的是**锁文件本身与矩阵冲突**：钉了一个要求 Py≥3.11 的版本，而矩阵含 3.10 → CI 失败。这类问题只有"CI 真的在跑"才会被发现。

**Y6｜失败输出要能定位** · `SHOULD` · `审`

CI 失败时，输出应直接指出"哪个文件、哪一行、什么规则"。只打印一行 `exit 1` 的门禁等于没有门禁。

**Y7｜门禁不得靠全局豁免维持绿色** · `MUST` · `审`

豁免必须逐点、带理由、可审计。按类豁免只在 `E2a` 的四条同时成立时可用。

> 判据：把门禁的豁免全部去掉跑一遍，看红多少处。红 0 处说明门禁是空的；
> 红几百处说明它基本靠豁免活着——两种都要追到具体原因，而不是继续加豁免。

## 十三、构建、发布与部署

**V1｜构建可重复** · `MUST` · `机`

固定工具链版本并**在 CI 里断言**（不只是写在文档里）；构建产物可溯源到 commit。

**V2｜版本注入单一来源** · `SHOULD` · `审`

版本号从一处产生（tag 或 VERSION 文件），编译期注入，运行时可查。

**V3｜部署脚本要过语法检查** · `SHOULD` · `机` · `[服务]`

`bash -n` / `sh -n` 覆盖全部部署脚本，并纳入 CI。

**V4｜回滚路径必须存在且演练过** · `MUST` · `审` · `[服务]`

数据库迁移、配置变更、镜像版本三者都要能回退。只前滚的系统，第一次需要回滚时就是事故。

> 纯库没有"回滚部署"，但等价物是**版本降级**：新版本写出的数据，旧版本读不读得动？
> 答案必须写进文档（"旧版不认识新字段，会忽略"或"旧版会拒绝，因此不可降级"）。
> 说"我们发版从不降级"不算答案，那是把风险留给用户。

**V5｜启动失败要区分"配置错"与"依赖不可用"** · `SHOULD` · `审`

配置错应当快速失败并给出可操作信息；依赖不可用允许降级并明确标记为降级状态。

> 纯库的等价物是**导入期与首次调用**：配置错在导入/构造时抛，且错误信息指出哪个键；
> 依赖不可用可以在首次调用时抛，但不能变成"看起来构造成功、一调就崩"。

**V6｜降级必须被观测到** · `MUST` · `测`

任何"启动失败但继续跑"的路径，必须在日志与健康检查里体现为 degraded。

> 失败模式：插件管理器/审计服务启动失败只打一条 `log.Printf`，服务继续跑。运维看到"进程在"，实际功能缺失。
> 纯库的"观测面"可以是返回值、状态查询 API 或结构化日志——但必须是**调用方读得到的东西**，
> 不能只在 stderr 里说一句。判据：降级发生时，有没有一个**非人眼**的消费者能知道。

## 十四、可观测性与可运维性

**O1｜结构化日志 + 稳定字段** · `SHOULD` · `审`

时间、级别、模块、错误码、业务 id（会话/请求/任务）必须结构化可检索。

**O2｜诊断入口** · `SHOULD` · `机` · `[服务]`

提供 `/health` 或等价物，能输出：装配了什么、版本是什么、哪些子系统处于降级。

> 纯库的等价物是一条 `describe()` / `info()` 之类的只读查询：版本、已装配的扩展点、
> 处于降级/禁用的子系统。它不是给运维用的，是给**调用方排查**用的——
> "为什么我的插件没生效"不该只能靠读源码回答。

**O3｜错误要可归类** · `SHOULD` · `审`

错误应能归到有限类别（上游失败 / 校验失败 / 内部错误 / 资源不足），而不是一团 `errors.New("something went wrong")`。

**O4｜关键的"静默失败"必须有告警面** · `MUST` · `审`

落盘失败、重试队列积压、降级状态：这些不会让进程崩，但会让数据不对。它们必须有计数或告警。

> "告警面"不等于"必须有监控系统"。计数、状态查询、返回给调用方的错误码都算；
> 唯一不算的是"只写了一条日志，而没有任何东西会去读它"。判据同 `V6`：
> 有没有一个非人眼的消费者。

**O5｜日志要能回答"刚才发生了什么"** · `SHOULD` · `审`

判据：给定一个用户投诉的时间点，能否在 10 分钟内定位到那次请求的完整路径。

## 十五、文档与 ADR

**D1｜架构文档要包含"真实的依赖方向"** · `MUST` · `审`

文档里的分层图必须与代码一致。若不一致，宁可写"当前存在倒挂（见 #123）"也不要画理想图。

> 失败模式：有 12 篇文档、3 个 README、一个 openspec 目录，但没有一篇说明真实的依赖方向其实有一条反向倒挂。新人按文档理解，必然误判。

**D2｜"未实现"要写成 ADR** · `SHOULD` · `审`

评估过但决定不做的方案（如子进程隔离），要留下：动机、代价、结论、何时重议。

> 价值：它阻止下一个人重复评估，也阻止"以为已经做了"。

**D3｜文档与代码的一致性要机器校验** · `SHOULD` · `机`

README 里的用例数、步骤数、门禁数，应能从代码/测试实际数量比对。

**任何由脚本生成的文档，都必须在门禁里"重新生成后比对"**，而不是生成一次就提交。

> 失败模式：README 写"21 步"，实际是 22 步。数字漂移本身不致命，但它说明"文档是手写的、没人维护"。
> 更糟的形态是半自动：仓库里有一个 `_gen_xxx_md.py`，文档是它生成的，但**门禁不调用它**。
> 于是文档在生成那一刻是对的，之后每一次改动都在让它过期，而且没有任何信号。
> 半自动文档比纯手写文档更危险——它看起来是可信的。

**D4｜强约束与软提醒分开写** · `MUST` · `审`

文档里要把"不满足就拒绝"和"提醒你留意"分开列表。

> 失败模式：把"写后提醒"写成"必须复核" → 后续维护者按"正确化"改造，把柔性的提醒改成刚性绑定，流程变卡、模型反复被拒。

## 十六、评审与合并

**Z1｜评审按"能不能被证明"组织** · `MUST` · `审`

每条评审意见应能指向：具体文件/行、违反了哪条准则、以及**如何验证**。

**Z2｜PR 要说明验证证据** · `MUST` · `审`

PR 描述里写清：跑了什么、结果如何、没跑什么、为什么。

**Z3｜改动可回滚** · `SHOULD` · `审`

一个 PR 应能被单独 revert 而不牵连其他改动（避免"顺手格式化"造成的纠缠）。

**Z4｜合并前清单** · `MUST` · `审`

见附录 A。

## 附录 B：反模式目录

| 反模式 | 为什么致命 |
|---|---|
| 扁平上帝包（数百文件同包） | 子域只存在于文件名前缀，门禁无法表达，拆分成本随时间指数上升 |
| 分层只禁单向 | 反方向倒挂会悄悄发生，分层成为命名装饰 |
| 只查层间、不查层内 | 同层互引逐条检查永远通过，该层却无法独立测试、无法按模块拆包 |
| 顶层 tuple 就当不可变 | 元素仍可变，事实源被下游改掉，事故点离改动点隔着三层调用 |
| `check-blank: false` + 大量 `_ = fn()` | 状态写入失败无痕，不触发任何告警 |
| 整族安全规则全局豁免 | 路径穿越/权限/注入同时失去提醒 |
| 惯用法表覆盖上百处且无上限 | 逐条都合理，合起来等于静默吞掉基本不检查，而门禁是绿的 |
| 门禁用子串匹配 | 改名即绕过，且给出"通过"的假象 |
| 两份检查清单 | 只会跑其中一份，且通常跑的不是最强那份 |
| 门禁在干净环境必然失败 | 长期红 → 全员忽略红色 |
| skip 无白名单 | 跳过项静默增长，覆盖度无声流失 |
| 上限写成 `len(白名单)` 再比较去重后的实际值 | 恒真的断言，门禁看起来在，永远不会红 |
| 覆盖率口径排除新模块 | 最需要守护的地方没有下限 |
| 仓库里有 `.coverage` 但门禁不跑它 | "有覆盖率"与"守覆盖率"是两件事 |
| 生成物文档进门禁前就提交 | 半自动文档看起来可信，实际从生成那刻起就在过期 |
| 攒到任务末一次性落盘 | 中途异常丢失整个任务（含用户输入） |
| 上层与下层都做重试 | 重复写入、重复坐标 |
| `assert` 做控制流 | `-O` 下退化为 AttributeError |
| 续跑判定不看取消位 | 无限自转，CPU 与事件流被打满 |
| 只记录哈希却暗示已校验 | 提供虚假安全信心 |
| 注释写过程叙述 | 三个月后全是过期信息 |
| 为已删模块保留转发层 | 新旧并存，无人知道哪个是活的 |

## 附录 C：门禁最小集合

新项目起步时，先建这 9 条，再按需加：

| # | 门禁 | 判据 |
|---|---|---|
